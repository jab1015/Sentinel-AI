## Purpose

Define a vault architecture that isolates item keys, minimizes plaintext exposure, supports independent recovery, persists authenticated metadata, and locks predictably.

## Key hierarchy

Current implemented hierarchy:

`credential protector -> VMK -> independent per-item Vault key -> independent SNTLENC1 container DEK -> item ciphertext`

Rules:

- The VMK never directly encrypts arbitrary user-file content.
- Every Vault item has an independent random 256-bit per-item key.
- Every encrypted container independently generates its own random 256-bit DEK.
- The container DEK is wrapped under the exact per-item Vault key by mode 4.
- Both wrapping layers authenticate Vault ID + immutable Item ID bindings.
- Rewrapping the VMK does not require re-encrypting every item ciphertext.
- Compromise/corruption of one item key must not cryptographically couple unrelated item ciphertext.
- Container nonce/key reuse is prohibited.

## Vault metadata

Durable metadata is now source implemented through `VaultMetadataStore`.

The metadata snapshot is encrypted/authenticated and includes:

- metadata format version
- Vault ID
- monotonic generation
- item identifiers
- ciphertext filenames
- verified plaintext lengths
- VMK-wrapped per-item key records
- transaction/recovery state

The metadata snapshot uses its own random encryption key wrapped by the VMK. Writes use an exclusive cross-process lease and a durability sequence of temporary write, flush, reopen/authenticate, commit, then final reopen/authenticate.

Metadata generations must increase monotonically. Rollback or out-of-order writes fail closed.

The item-store layer also rejects authenticated but internally ambiguous metadata, including duplicate/empty item IDs, duplicate/empty transaction IDs, multiple pending transactions mapped to the same item, duplicate/blank ciphertext identities, pending transactions with no matching item metadata, mismatched Vault/item key bindings, and invalid ciphertext filename confinement.

Do not store original full source paths in plaintext by default. The current item metadata does not persist the original source path.

## Lock state

The service has explicit states:

- Locked
- Unlocking
- Unlocked
- Locking
- RecoveryRequired
- Corrupt

No operation may infer `Unlocked` merely because a prior operation succeeded.

The key-session source invalidates in-flight unlock attempts when a lock epoch changes. This prevents a password/recovery/Windows unwrap operation that began before a Windows session lock from completing afterward and silently returning the Vault to `Unlocked`.

Vault item encryption/opening refuses key release when the Vault is locked or when the Vault/item identity does not match the authenticated mode-4 record.

## Unlock modes

Source key-protection modes available to the Vault foundation:

- Windows current-user
- password using bounded Argon2id parameters plus authenticated AES-GCM wrapping
- independent recovery key

Future Windows Hello/TPM integration is a separate reviewed feature and must not silently change recovery semantics.

## Automatic lock

Lock on:

- configured inactivity timeout
- Windows session lock
- explicit user lock
- app shutdown
- security-sensitive state transition where key retention cannot be justified

Current source implements inactivity transition and a session-lock service hook. Wiring the hook to actual Windows session notifications remains **WINDOWS RUNTIME / APP INTEGRATION REQUIRED**.

On lock:

- reject new plaintext operations
- reject mode-4 container key recovery
- clear retained VMK/item-key buffers where meaningful
- close plaintext-bearing streams/handles

## Plaintext handling

Vault add-item encryption uses the existing verified `SNTLENC1` engine and writes a separate ciphertext output. The source plaintext is not modified or deleted by the add-item transaction.

Current rule:

`encrypt -> flush -> reopen/authenticate -> verify -> commit Vault metadata`

Plaintext removal is intentionally a separate future operation. A successful Vault add must never be treated as authorization to erase the source.

If a temporary plaintext file is ever required by a future open/edit workflow:

- create it only inside a dedicated restricted directory
- use exclusive creation and restrictive ACLs
- record it in a cleanup transaction before plaintext is written
- keep its lifetime minimal
- never place it in generic `%TEMP%` without additional protection
- verify cleanup
- report cleanup failure as `REMAINS`
- recover cleanup state after restart/crash

No temporary-plaintext Vault extraction implementation exists at this checkpoint.

## Add-item transaction

Source implemented in `VaultItemStoreService`.

Current transaction:

`validate source -> acquire cross-process Vault-operation lease -> validate storage boundary -> create item identity/per-item key -> commit Prepared metadata -> create/flush/authenticate/verify SNTLENC1 ciphertext -> commit CiphertextReady -> commit MetadataCommitted -> reverify metadata + ciphertext -> clear pending transaction`

Important invariants:

- source must be fully qualified, existing, and non-reparse
- Vault must be explicitly unlocked
- new item operations refuse to start while recovery is pending
- deterministic ciphertext filename is derived from immutable random Item ID
- pending item metadata exists from `Prepared` onward but is never surfaced by the committed-item view
- ciphertext must authenticate with the exact Vault ID + Item ID and verified plaintext length before completion
- original plaintext remains untouched on success, failure, cancellation, or recovery
- a final item is not considered committed until the pending transaction has been durably cleared and reread

## Open / export transaction

Authenticated key recovery through mode 4 is source implemented and is used by verification/recovery. A user-facing verified export/open-to-separate-destination operation is the next implementation milestone.

Required rules for that operation:

- locate only a committed item by exact Item ID
- require the Vault to be unlocked
- authenticate/decrypt through the existing container engine
- write only to a separate destination that does not already exist
- never overwrite a destination
- leave Vault ciphertext and metadata untouched
- never use export success as authorization to delete the Vault item or any source plaintext

## Crash recovery

Durable transaction states are source implemented:

- Prepared
- CiphertextReady
- MetadataCommitted
- CleanupPending
- Complete

Current recovery behavior:

- `Prepared` with no ciphertext: remove only the incomplete item metadata + pending transaction
- `Prepared` with ciphertext: ciphertext must authenticate fully before promotion
- `CiphertextReady`: reverify before promotion to metadata committed
- `MetadataCommitted` / `Complete`: reverify before clearing pending transaction
- ambiguous metadata or ciphertext fails closed
- `CleanupPending` deliberately remains unimplemented because source-plaintext removal is a separate future privacy operation

Recovery is designed to be idempotent and refuses to guess when state is ambiguous.

## Storage-boundary hardening

Current source validates the Vault root and `items` directory when the service is created, and revalidates them again after acquiring the operation lease and before recovery-sensitive use.

It requires:

- Vault root and item directory still exist
- canonical item directory remains exactly `<vault-root>/items`
- root/item directory final filesystem entries are not reparse points
- item ciphertext filename is a simple filename confined beneath the item directory
- recovery ciphertext itself is not a reparse point

This materially narrows path/junction hazards but is **not claimed to be a complete exact-handle directory-identity fence against every possible ancestor/rename race**. That remains part of adversarial Windows runtime qualification and future hardening if evidence identifies a remaining bypass.

## Logging

Never log VMKs, per-item keys, container DEKs, passwords, recovery keys, or decrypted filenames/paths unless a separately reviewed privacy policy explicitly permits a bounded sanitized representation.

Current Vault source does not intentionally log key material.
